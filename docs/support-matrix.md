# Support matrix (generator 0.1.0)

A capability must be declared to generate its public helper. Both targets implement the declared contract through bundled compiled codecs, with the target differences described below. A missing provider capability is not inferred from a payment resource name or field name. GET/HEAD/OPTIONS have bounded default retries; mutation retries and idempotency still require declarations.

Runtime safety in both targets includes a default 1,000-page pagination cap, continuation-cycle and consecutive-empty-page detection, distinct timeout/deadline errors, and consistent decimal-seconds/GMT HTTP-date `Retry-After` parsing. See [errors and retries](using-sdks.md#errors-and-retries) and [pagination](using-sdks.md#pagination-and-polling).

Both runtimes track retry-chain outcomes and caller retry eligibility, preserve completely read successes past the deadline, and accept per-operation timeout/deadline defaults with request > client > operation > global precedence. See [errors and retries](using-sdks.md#errors-and-retries) and [operation time budgets](configuration.md#operation-time-budgets).

Node webhook verification returns `VerifiedWebhook`, including `reason` when `known` is false. Declared verification also has a standalone `verifyWebhook` export at the root and `webhooks` subpath and PHP `Webhooks::verify` method requiring no client configuration. PHP multi-variant/ambiguous events return validated `stdClass` values rather than generated event classes, even when `known` is true. PHP omits the standalone class when a model uses the `Webhooks` name (case insensitive); the model and `Client::verifyWebhook` remain available. The package root exports `KnownWebhookEvent` and one `<EventName>Event` type per event. Per-event types use the PHP event naming rule and match class names where PHP emits an event class; multi-variant events have Node types without corresponding PHP event classes. Top-level event fields support exhaustive narrowing. See [webhook verification](using-sdks.md#webhook-verification) for payload annotations and dotted event paths.

PHP errors expose `KIND_*` and `OUTCOME_*` constants, append available HTTP status/code/request-ID context to server messages, and return the HTTP status from `getCode()` (0 without a response).

`include` selects named operations before validating their wire capabilities and skips operations without a nonempty `operationId`. Without `include`, unnamed operations fail diagnosis; `hidden` and audience declarations need an operation ID. Declared IDs must remain unique throughout the document. Request bodies declaring only unsupported media types fail directly; exclude those operations with `include` or `hidden`.

Body-driven retry configuration (`errors.retry`), capped half-to-full backoff (`retry.maxDelayMs`), prefixed automatic UUID v4 keys, error/result key exposure and required-key TypeScript options are supported in Node and PHP. HTTP 412 and cancellation never retry. Retry waits that exceed the deadline preserve the last error; mid-flight deadline expiry remains a deadline error.

Clients use the first declared top-level server as their default URL; explicit `baseUrl` overrides it. Only absolute HTTP/HTTPS server URLs without credentials, query, fragment or variables are supported. An absent/empty server list requires an explicit URL. HTTP always requires `allowInsecureHttp`, including localhost and anonymous APIs.

Both targets omit headers supplied by the operation's permitted authentication modes and configured API-version headers from method inputs while validating their supplied values before dispatch. Credential headers are validated by their wire representation. Anonymous operations and operations whose modes never supply a declared header retain that input field. Declared idempotency, conditional and outgoing request-ID headers retain input fields and their declared requiredness is enforced before dispatch; idempotency and conditional values can also come from request options or automatic idempotency keys. API responses and verified webhooks use the same numeric codecs; their respective schemas determine whether integers are exact strings or native safe integers.

Both targets omit schema `example`/`examples`/`default` annotations at sensitive, write-only or password locations, including protected ancestors, references and compositions. A protected dictionary or element constraint protects every child location of the same value across composed schemas. This never promotes that containing value or its siblings to protected values. Runnable samples use placeholders. Source-graph publication protection persists in private generation records; restored regeneration and release preparation use the same decision. See [documentation and examples](configuration.md#documentation-and-examples).

Node response declarations use referenced component names and collapse identical effective declarations to one canonical name (shortest, then alphabetical). Different requiredness, nullability or profile shapes retain separate names. Payload methods expose concrete types or unions; only request-reachable models have input types and factories. PHP retains its compiled response class identities.

Both targets compare HTTP/HTTPS origins without scheme or host case distinctions and normalize default ports. Nondefault ports remain distinct origins, including for pagination links. Explicit `allowedOrigins` entries must be canonical origin strings with default ports omitted. Error paths traverse JSON objects and array indices, and scalar values have no child fields. Error messages, provider codes and code-based retries require original JSON strings; exact numeric preservation in parsed details does not convert JSON numbers into valid messages or codes.

OpenAPI 3.1 schema `$ref` siblings intersect with the referenced constraints. OpenAPI 3.0 Reference Object siblings are ignored; 3.1 Reference Objects outside schemas apply supported `summary`/`description` overrides and ignore other siblings. Path Item references combine nonoverlapping fields in both versions. See [reference siblings](configuration.md#reference-siblings) for examples and conflict rules.

Descriptions, examples and defaults are metadata, not evidence of server behavior. Declared exact formats determine serialization. Generated inputs preserve presence without inferring whether a null clears data on the server.

OpenAPI 3.1 type arrays normalize during loading: `["object", "array", "string"]` becomes an equivalent `anyOf`, preserving sibling constraints, and `["null"]` becomes `type: "null"`. Public dynamic schema-taking helpers do not run this loader normalization; use explicit `anyOf` or `type: "null"` there. See [schema-taking helpers](using-sdks.md#schema-taking-helpers).

`propertyNames` accepts string `type`, `minLength`, `maxLength`, portable `pattern`, and string `enum`/`const`. It checks every object key, including declared properties, in request validation and strict response decoding. Lengths count Unicode code points. Key enums and constants stay closed in responses because they constrain object shape; ordinary response enum values remain open. TypeScript and PHP dictionary keys remain strings. Other key-schema keywords fail loading with a supported-subset remedy.

Exact numeric enum membership and numeric composition merging compare mathematical values, including equivalent decimal/exponent spellings. Exact numeric enum inputs use strings for `number` with `format: "decimal"`, `int64`, and `uint64`, including single-element type arrays. Plain number/float/double inputs use native numbers, including numeric enums. Their outputs use floating-point precision; overflow to a non-finite value produces a protocol error. Mutually dependent unions are matched jointly under a bounded search; an unusually ambiguous schema can exhaust it and fail validation.

Integer response decoding accepts integral decimal/exponent tokens without floating-point rounding. Exponent expansion is limited to 10,000 appended zero digits to bound allocation; larger expansions produce a protocol error. Decimal precision and the public representation of unknown numeric fields are preserved. Sparse Node input arrays are rejected, including arrays in additional fields.

Undeclared 2xx statuses reuse the sole declared JSON 2xx response only when neither an exact declaration nor `default` exists. Multiple candidates, non-JSON kinds and redirects are not inferred. Required fields remain enforced; schema errors expose the failing field path and preserve the buffered JSON body for explicit recovery in both targets. Node additionally certifies decoded response values and projections against the emitted TypeScript plan; incompatible success payloads and pagination items fail with a protocol error, and incompatible error details become undefined with raw recovery retained. Future object variants keep unknown field types until explicitly narrowed. See [response recovery](using-sdks.md#successful-http-responses-and-schema-drift).

HTTP success bodies and verified webhook payloads must contain well-formed UTF-8 JSON without a byte-order mark or unpaired surrogate escapes. Malformed bodies produce a protocol error; decoding never repairs them by inserting replacement characters. HTTP error statuses remain available even when their bodies cannot be parsed.

Offset pagination requires compatible SDK representations: int64/uint64 continuations require int64/uint64 query parameters. Cursor parameters must be scalar strings, and offset parameters must be scalar integers. Incompatible declarations fail diagnosis.

## Compatibility analysis limitations

Compatibility checks compare public declarations and runtime guarantees separately. Losing required keys in mixed objects or nested dictionary values is breaking even where TypeScript exposes `unknown`. Added-result inclusion covers explicit scalar/object/array types, dictionaries, nesting, null and absent bodies. References, complex compositions, nullable type unions and arbitrary result unions retain review findings where inclusion cannot be proved; their execution support is unchanged.

Nested constraint changes in `allOf`, `anyOf`, and `not` can receive only a `review` finding even when they break existing inputs. The SemVer release policy relies on provider judgment for these findings. See [known compatibility limitations](releases.md#known-compatibility-limitations).

## Unsupported capabilities

- File uploads, multipart bodies, binary response media other than PDF, and download resume/checksum protocols. PDF downloads are buffered; general-purpose file streaming is outside the current contract.
- Built-in OAuth refresh, cloud and non-GitHub CI subject-token sources and CLI-process credentials. Declared [default credentials](using-sdks.md#default-credentials) support environment, token-file and GitHub Actions federation with process caching in both targets. Other tokens can be supplied as strings or [credential providers](using-sdks.md#credential-providers).
- Bulk helpers, additional protocols and languages, adaptive throttling, caching and dirty tracking, framework packages, checkout UI, portals, forwarding and replay services, and time simulation.

The schema can still express per-item bulk results, resource relationships, next actions and exports as ordinary data. Automatic provider behavior requires a declared capability, except for bounded default retries on GET/HEAD/OPTIONS; a resource property alone never triggers network activity.

Undeclared optional capabilities produce no helper. Unsupported or incomplete capability declarations produce diagnostics. An operation with unsupported wire semantics fails generation rather than shipping as a working SDK.

`multipleOf` uses exact decimal divisibility. Work that requires more than 10,000 appended digits fails validation; power-of-ten divisors need no expansion. `const` and `uniqueItems` compare JSON values with exact numeric equality and order-independent object keys; array order remains significant. `contains` requires a matching element in schema validation and strict variant guards; `minContains` and `maxContains` remain unsupported. Constants are never inserted automatically.

`dependentRequired` preserves property dependencies through equivalent conditional constraints. A present trigger requires every listed property; absent triggers impose no requirement. Dependency maps must contain arrays of unique property names.

Operation naming supports tag inference (default) and opt-in path inference in both targets. Path mode checks explicit naming reasons and method verbs during diagnosis, and resolves pagination helper collisions automatically. `void`, `close`, `delete` and `list` are portable method names; `new` remains reserved.

Positional requests support object-only `oneOf` and `anyOf` bodies in both targets, including referenced variants. Query/header parameter conflicts and typed dictionaries are checked in every branch. Per-operation object request overrides are rejected.

Both targets name positional params and preserve path/query parameter descriptions. Declared idempotency headers are accepted only through `idempotencyKey` options, with the original wire schema enforced. PHP uses `clientRequestId` for caller correlation.

Opt-in scalar query arrays are supported in Node and PHP for exploded form array parameters. Scalars normalize to singleton arrays before validation; other parameter encodings retain their original input shapes.

Integer representation defaults to exact int64/uint64 strings. Opt-in `integers: "number"` uses safe native numbers in both targets; the object form accepts `exactComponents` for exact integer subtrees such as Money. Both targets reject unsafe values without rounding.
